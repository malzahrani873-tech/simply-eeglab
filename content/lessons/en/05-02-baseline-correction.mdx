## The idea

Each epoch starts from a slightly different level, because of slow drifts left after filtering or small changes in electrode contact. This offset is not a response to the stimulus, but it is added to every point in the epoch.

The fix: take the moments before the participant sees the stimulus, called the <En>baseline</En>. Compute their mean in each channel and epoch, then subtract it from the whole epoch.

So which pre-stimulus period do you choose, and how do you subtract it?

Look at the shaded period: before correction the lines start at different levels, and after it they meet around zero. Any change after the stimulus is now measured relative to what came just before it.

## Why do I need it if the filter already removed most of the drift?

The high-pass filter in [the filtering lesson](/en/lesson/filtering/) removed most of the drift, and the official tutorial counts it as a form of baseline correction. But the offsets left between epochs are still enough to affect the average, so baseline correction is a standard step in ERP analysis.

## How do I correct the baseline from the menus?

Start with the dataset `D1 epochs` open. If you don't have it, open "Script to reach this state" at the top of the lesson.

1. Open <MenuPath>Tools > Remove epoch baseline</MenuPath>.
2. The <UiLabel>Baseline removal - pop_rmbase()</UiLabel> window opens. In <UiLabel>Baseline latency range ([min max] in ms) ([ ] = whole epoch):</UiLabel> the default is `-1000 0`, the whole pre-event period. Change it to `-200 0`.
3. Leave <UiLabel>Or remove baseline points vector (ex:1:56):</UiLabel> empty. It is an alternative that uses point numbers instead of time.
4. Leave <UiLabel>Channel type(s)</UiLabel> and <UiLabel>OR channel(s) (default all)</UiLabel> empty, so the correction applies to all channels.
5. Press <UiLabel>Ok</UiLabel>. In the new-dataset window, type `D1 epochs bl` in <UiLabel>Name it:</UiLabel>, leave <UiLabel>Overwrite it in memory (set=yes; unset=create a new dataset)</UiLabel> unchecked, then press <UiLabel>Ok</UiLabel>.

<Callout type="note" title="Milliseconds, not seconds">
Time in this window is in milliseconds, while the epoch limits in [the epoching lesson](/en/lesson/extract-epochs/) were in seconds. Type `-200 0` here, not `-0.2 0`.
</Callout>

## How do I correct the baseline with a script?

```matlab
% Subtract the mean of -200 to 0 ms from every channel and epoch
EEG = pop_rmbase(EEG, [-200 0]);
EEG.setname = 'D1 epochs bl';
EEG = eeg_checkset(EEG);

% Check: the baseline mean should now be close to zero everywhere
blIdx = EEG.times >= -200 & EEG.times <= 0;
blMeans = mean(EEG.data(:, blIdx, :), 2);
fprintf('Baseline points: %d, largest baseline mean: %.2g uV\n', sum(blIdx), max(abs(blMeans(:))));
```

## Which baseline period should I choose?

| Setting | Value | Why |
|---|---|---|
| Baseline for ERP analysis | -200 to 0 ms | A common value in ERP studies, used for example in the N400 experiment of the ERP CORE data. Short enough to sit close to the stimulus, long enough for a stable mean. |
| The whole pre-event period | -1000 to 0 ms | The default in the EEGLAB window. A more stable mean because it uses more points, but it may include activity from the previous trial when trials are close together. |
| A very short period | 100 ms or less | The official tutorial advises avoiding it when possible, because the mean of few points is noisy. At 128 Hz, 100 ms is only about 13 points. |
| Our path on this site | -200 to 0 ms | 26 points at 128 Hz. The same value for every participant and every condition. |

**Rule:** choose the baseline period before you see the results, and apply it unchanged to all participants. Changing it after seeing the waveform changes your result.

## How do I check that the correction worked?

- Run the check lines at the end of the script: there are 26 baseline points, and the largest mean is very close to zero (below 0.001 µV).
- Open <MenuPath>Plot > Channel data (scroll)</MenuPath>: every epoch starts near the zero line in every channel.
- The number of epochs did not change: <UiLabel>Epochs</UiLabel> in the main window is still 80.

## What are the common mistakes in baseline correction?

- **Typing the time in seconds.** The window expects milliseconds. `-0.2 0` means a 0.2-ms period, so only the zero point falls inside it, and the "correction" subtracts the value of a single point.
- **Keeping the default without thinking.** The default here is the whole second before the stimulus. That is not wrong, but it is a decision you should make on purpose and report in your paper.
- **A baseline that contains a response.** If another event (a button press or an earlier stimulus) falls inside the baseline period, you subtract a real response from the whole epoch. In D1, trials are 3 seconds apart, so -200 to 0 ms is clean. The default -1000 to 0 ms period, however, contains the first square in the second trial, which is one more reason to choose -200.
- **A difference before the stimulus.** If two conditions already differ during the baseline (for example, a slow wave that starts before the stimulus), correction turns it into a reversed difference after the stimulus. Look at the whole waveform from -200 ms, not only after zero.
- **Correcting the baseline before ICA.** The official tutorial warns that baseline correction adds random offsets to each channel, which ICA does not handle well. On our path, ICA runs before epoching, so this is not a problem.
